# Bike Portal cycling event ingestion replacement plan

Research and implementation specification | 8 October 2026 | Approved A1-A7 revision

Prepared for the Bike Portal owner and implementing developer

## 1 Executive summary

Replace the previous event ingestion work with a small, evidence-backed pipeline that discovers Texas cycling events, verifies organizer authority, refreshes known events every day around 6 a.m. America/Chicago, and publishes only validated facts. Reuse Bike Portal's Cloudflare Worker, D1 database, existing event IDs, rendering components and tests. Introduce durable source jobs, immutable event revisions and one controlled publication path. Start with deterministic adapters and automatic validation; add browser rendering, an LLM, Queues or Workflows only when a demonstrated source or workload needs them.

The existing retained checkout is a dirty development worktree, not the deployed application. Its old refresh scripts are local review prototypes with a disabled registry, no configured cron and no canonical writer. The deployed release retains 11 bundled Texas events alongside separate D1-backed events. The main integration risk is conflicting readers and hard-coded overlays, not a missing crawler alone. One new event repository must supply the homepage, API, both event route families, maps and calendar output consistently while preserving member ride plans. [R1-R8]

Use organizer sources as evidence; registration platforms and directories may discover candidates but do not automatically settle contradictions. Missing optional fields stay null. Record the exact evidence behind every published non-null fact, including date precision, timezone, source time and extraction version. Cancellation requires an explicit authoritative notice; a disappearance, weather forecast, HTTP error or closed registration is not cancellation. [P1-P3; S1-S8]

The approved A1-A7 controls make supported deterministic sources a zero-model normal path, reuse validated extraction across retries and days, share identical source requests, and checkpoint durable stages. Any necessary model receives a compact evidence envelope and returns a narrow validated patch. Mechanical transformations, validation and routine reports stay in code. Measure token use against the same completed work; no token saving has yet been demonstrated. C1-C8 remain conditional optimizations, not implementation or release prerequisites.

The minimum release condition is concrete correctness and recoverability: supported-source access, critical-field and provenance tests, safe replay and partial failure, compatible readers, and a proven code-and-data rollback. Healthy records advance independently of failed sources. There is no traffic, SEO ranking, source-count quota, mandatory human tester count or waiting-period condition. This task produces the plan only; implementation, remote migration, activation, deployment, credentials, spending and deletion remain outside its authorization.

## 4 Source onboarding and extraction

Keep a small machine-readable source registry in D1 or checked configuration, with source_id, organizer identity, source URLs and allowed hosts, authoritative scope, access basis and checked date, adapter and parser version, timezone evidence, discovery versus detail roles, update cadence, robots/terms references, pagination strategy, and enabled/paused reason. An organizer-controlled domain or an explicit organizer link to a registration page can establish the authority relationship once. Search results and directories are leads. Require a source-specific account or permission only when that source actually needs one. [P1-P3; S1-S4; S9]

Start with the existing organizer URLs and RunSignup public race discovery. RunSignup documents unauthenticated access to public races, while authenticated requests may be limited to races accessible to that account. Use state/date and pagination filters, then retrieve race/event details. Its race identity may persist across years, and endpoint date fields have different timezone semantics. Treat race ID, edition and child event ID separately; registration close is not the ride start. API availability is not permission to republish all content or photographs. [S1-S3]

BikeReg is a conditional discovery/detail adapter. Its official search documentation recommends AthleteReg GraphQL and exposes application, state/date, category and cursor fields. Prefer a verified static identity over a reusable vanity URL. Preserve calendar splits and category dates. The REST documentation describes first-100 results but also lists startpage; test real pagination and completeness rather than relying on either wording alone. No production API payload or access entitlement was tested in this planning task. A BikeReg access problem does not block RunSignup or organizer feeds. [S4]

For organizer sources, prefer published JSON/API or ICS, then event-specific JSON-LD, then deterministic HTML selectors. OpenGraph can identify an image candidate but cannot establish event identity, image rights or event dates. Associate all evidence with the exact event edition before accepting it. Maintain a small supported-adapter set, expanding by demonstrated coverage needs. No mandatory number of initial sources or records is needed.

### Extraction and escalation contract A1 A4 A5

The normal path for a supported deterministic source makes zero model calls. Code handles date and unit normalization, supported RFC recurrence, identity rules, evidence metadata, schema validation, test reporting and routine operational summaries. Do not add a model reviewer or narrator to every event or run. This is a design target for the normal path, not a token-based release gate. [P2-P3; A1; A5]

Escalate only an unresolved, material semantic question supported by accessible source evidence that the maintained adapter cannot safely interpret, such as whether a qualified organizer notice applies to one distance or the whole event. Record the reason, affected occurrence and fields, evidence coverage and adapter version before calling a model. Missing optional information, mechanical formatting, transport failures, credentials, schema errors and an unfinished adapter do not alone justify escalation. Retry transport failures through the job policy; quarantine unsupported structure or improve the adapter. NOT_SPECIFIED requires adequate inspection of the relevant authoritative evidence, never merely a parser's failure to find a field. An inaccessible source remains UNKNOWN.

If a model is necessary, send one typed, compact evidence envelope: an unambiguous dictionary of source/observation/occurrence IDs; event edition and relevant timezone or temporal anchor; current values only when needed to interpret the question; the requested unresolved fields; and complete relevant statements with locators and scope. Keep negation, conditions, exceptions and linked notices. Select evidence by explicit source structure and required meaning; do not blindly truncate a page or rely on stale structured data while discarding a current visible notice. If evidence completeness cannot be established, hold or broaden retrieval instead of claiming certainty. [A4]

The model returns only allowed field patches containing value, value state and evidence IDs/locators or offsets. Code validates locators against the captured evidence, builds provenance and metadata, merges the patch with unchanged fields, and validates the complete resulting record and cross-field invariants. Reject extra fields, unsupported claims, invalid references and truncated/malformed outputs. Do not ask the model to repeat unchanged records, verbose explanations or routine validation results. An optional audit rationale must be short and tied to the unresolved decision. Page text remains untrusted data: it cannot execute tools, select new authority, change policy or publish. If substantiation fails, isolate the affected field or occurrence; the pipeline remains usable without a model or browser service.

### Shared observations and validated reuse A2 A3

Separate four identities: the scheduled source job, a fetched representation, an extraction interpretation and an event occurrence. A source job's daily key must not force re-extraction; a reusable page URL must not collapse different annual editions. A request identity includes method, normalized semantic query/body parameters, relevant headers/language, access scope and rendered versus raw representation. Do not store secret header values in keys or logs; use an internal access-context identity. Treat incidental transport parameters as irrelevant only when the adapter proves that is safe.

Share identical fetches and deterministic page parsing within a run and across concurrent jobs through a durable singleflight lease with a fencing token. The old registry's Old Dennis and La Bella Pop entries use the same lonestarrandon.org/calendar representation: fetch and parse it once for an identical request, then select evidence for each distinct event. One shared page never means shared occurrence identity or permission to apply a cancellation to every event on the calendar. Preserve per-event assertion, conflict and status checks. A failed leader releases or expires its lease so another job can retry safely; stale leaders cannot commit. [R3; A3]

Fetch on the required schedule, using conditional requests where supported. Store retrieval result, body hash, ETag/Last-Modified, relevant-content hash and linked-detail/notice observations. A 304 updates successful retrieval time for that representation, not its source publication time. Unchanged calendar HTML does not exempt linked notices or known event details from their required checks.

Cache only validated extraction successes by evidence identity plus interpretation context: source and access scope, authoritative scope, event/edition/occurrence, timezone and temporal anchor, requested fields, parser/schema versions and, where applicable, prompt/model/configuration versions. Versions cover the semantic rules that can change the answer. A relevant-content hash is safe only when the adapter can prove that no excluded material changes interpretation, including new notices. Default to broader invalidation when uncertain. URL-only, title-only, body-hash-only or semantic-similarity keys are insufficient. Changed source authority, context, requested fields or relevant versions invalidates reuse even if the bytes match. [A2]

Persist successful extraction before proceeding to reconciliation and publication. Reuse it across daily checks, retries and downstream crashes only after validating its key and completeness. Freshness comes from current successful observations and current reconciliation, not a cache timestamp. Re-evaluate authority, competing claims, linked notices and publication version before a recovered result becomes visible. New evidence arriving during recovery invalidates affected candidates; a cache hit cannot bypass a cancellation or conflict. Reparse retained permitted evidence when parser rules change instead of refetching unnecessarily, while still performing current due observations. Transport errors, missing evidence, malformed outputs and timeouts are not successful extraction entries; conditional reuse of stable unresolved outcomes is C5, not the baseline cache contract.

Respect source-specific terms, robots rules, rate limits and access restrictions. Robots permission does not itself grant a content license. Store minimal factual extracts and private evidence under a documented access basis; retain only what is needed. Record the main image URL when actually supplied, but display, hotlink or archive image bytes only where the source permits it. No image or extended-description clearance should hold up otherwise permitted factual event data. [S9-S10]

## 5 Data model and fact rules

Use additive ingestion tables. A compact initial design is sources, ingest_jobs, source_observations, extraction_results, event_revisions, event_aliases and event_publication. Use existing D1 rows and versioned JSON for request leases, stage checkpoints, extraction keys and usage counters; add a separate table only when its query or uniqueness requirement warrants it. No separate cache service, vector database or generic dependency platform is required. Keep field assertions inside versioned revision JSON initially rather than creating a table for every field. Index due jobs, source identities and current event lookup. Existing events remains the stable identity anchor for member references; its legacy content is a baseline revision. Do not use raw_json as an unaudited overwrite escape hatch.

| Domain | Required representation and rules |
|---|---|
| Identity | Internal immutable event ID; source ID and source record ID; edition or season; optional series ID; occurrence ID and original recurrence key; old slug/ID aliases. A reschedule retains identity. A new annual edition gets a new occurrence. |
| Date and time | Original text, date-only or date-time precision, all_day separate from unknown time, local date/time, IANA timezone with evidence, UTC instant only when determinable, end and end semantics, previous dates and change reason. Unknown end stays null. |
| Places and routes | Start and optional finish location separately; venue/address/city/state and source precision; coordinates with origin/precision. Separate route description, official route page, map URL, GPX/KML reference and verified geometry. |
| Cycling facts | Discipline, participation format and purpose; original source category retained. Distance options carry values, units and qualifiers; route/category association preserved. Store surface, technical difficulty and slope/grade separately. No universal difficulty conversion without a documented mapping. |
| Rules and media | Bike/e-bike permission, equipment and eligibility rules with explicit required/prohibited/unknown states; main image URL and use status. Missing picture, finish, route or equipment rule does not reject the event. |
| Status | Event: scheduled, cancelled, postponed, rescheduled, completed or unknown. Registration: open, closed, sold_out or unknown. Source health and validation state remain independent. Elapsed date means past/completed-for-browsing, not proof the ride took place. |
| Evidence | For each assertion: normalized and original value, value state, source URL/locator, minimal supporting text, observation ID/hash, retrieved_at, source_updated_at if present, method/parser version and authority relationship. Preserve competing assertions and chosen-value reason. |

Keep extraction_results immutable and distinct from source observations and published revisions. Each result records its full interpretation key, evidence references, completeness/validation state and producing versions. Job checkpoints reference the successful stage output and its preconditions; reconciliation records selected and competing assertions plus the authority/evidence version it used. Store enough structured usage data to distinguish a new extraction from recovered work. Retention must preserve evidence and result references needed by current publications and unfinished recoverable jobs. [A2; A7]

For recurrence, use a maintained RFC 5545 library after checking its current compatibility and license during implementation. Preserve UID and original RECURRENCE-ID, RRULE, RDATE, EXDATE, overrides, SEQUENCE and source timestamps. A moved occurrence keeps its original recurrence identity. Expand only a bounded rolling window, proposed default 12 months, with count limits; preserve the source recurrence so later windows can be generated. Do not treat annual reuse of a URL as an RFC recurrence rule. [S5]

Date-only values remain dates. Never coerce unknown time to midnight or label it a confirmed all-day event. For calendar export, use a date placeholder explicitly labeled “time not supplied” if exporting a date-only unknown-time event, and disclose that limitation; use true all-day semantics only when supported. DTSTART is inclusive and DTEND exclusive; multi-day inclusive display dates must be converted deliberately. Keep original dates for cancellations or indefinite postponements, and new plus previous dates for reschedules. Never use registration dates as event dates. [S3; S5-S8]

Publish the useful facts available: verified identity, organizer authority, Texas location basis and an interpretable date or explicit postponed/TBD status. Exact street address, geometry and an image are optional. An unresolved start date removes the occurrence from date-filtered upcoming results while preserving its detail page and explanation. A city-only location gets a city label, not a precise start pin. Cross-border rides qualify when the verified start is in Texas; record any route crossing explicitly. That is the proposed scope default, not a claim of statewide completeness.

## 6 Deduplication conflicts and freshness

Deduplicate first by source IDs scoped to edition/occurrence, then by organizer-confirmed links or an already resolved alias. Same title, date and city generate a possible match, never a destructive automatic merge. Distances and race categories under one organized event remain child options unless the source establishes distinct occurrences. Track both source identities even when one public event is created. Use the existing crosswalk only as a candidate list, including its unresolved location conflict. Preserve old slugs and member-linked IDs. [R4-R7; S3-S5]

Choose facts by authoritative scope, occurrence identity and recency of the actual notice. A dated, unambiguous organizer cancellation notice can override stale JSON-LD automatically. A registration host controls registration availability when delegated by the organizer, but does not necessarily settle a conflicting route or start location. Material disagreement between equally authoritative current sources holds the affected field or occurrence; retain both claims and a reason. Optional distance or image conflicts do not block an accurate date/location listing.

An event that disappears is “not observed” until an explicit cancellation or defensible expiry rule applies. Mark incomplete discovery runs as incomplete; never diff them into deletions. Refresh known upcoming IDs and their notice pages even when a discovery query stops returning them. Preserve cancelled/postponed detail pages and calendar status. Do not infer a cancellation from rain, a weather forecast, a 404, a failed request, registration closure or a whole-source outage. [P2; S6-S8]

Track last_attempt_at, last_successful_fetch_at, last_semantic_verification_at and source_updated_at separately. Show the meaningful check date beside facts. Proposed default: mark an event/source stale once its next daily refresh is missed and report lateness; retain the last known good revision with that label. If a critical fact is disputed, exclude only that occurrence from attendance-oriented upcoming results. Keep source failures from erasing healthy records. Faster checks near event time are optional and source-permission dependent, not a release prerequisite.

## 7 Minimal reliable execution and publication

Use the existing Worker and D1 with a durable due-job table. One scheduler scans due work; local and preview runs call the same orchestration code without a schedule. A proposed hourly UTC wake-up computes the next 06:00 America/Chicago due time, claims pending jobs and resumes unfinished ones. The daily fetch frequency stays once per source unless retry or correction work is due. This handles DST, delayed triggers and missed invocations without one cron per source. Do not merely skip every wake-up except exact hour six. [S11]

Jobs have source ID, due local date/time, adapter version, unique idempotency key, attempt count, next_attempt_at, lease expiry and a fencing token. Atomically claim work; commit only with the current lease/token. An expired lease can be reclaimed automatically. Keep this source-job lease distinct from the shared-request singleflight lease and the extraction interpretation key. Distinguish completed, partial, deferred, permanent failure and retryable failure. Do not mark a whole daily run successful because all sources returned zero candidates. Discovery completeness and known-event refresh completeness are separate results.

Checkpoint four explicit stages: observation, validated extraction, reconciliation and publication. Commit a successful stage output durably before recording the next stage as due. On resume, verify the preceding output and its evidence/context/version preconditions, then restart from the earliest invalidated stage. A downstream database or publication failure must not normally repeat a completed extraction or model request. A new authoritative notice, changed identity/context or superseding publication forces affected reconciliation to run again. Never mark the whole job complete before all required outputs and completeness results are committed. [A2]

For optional model calls, deduplicate the logical request by extraction key and record pending/success/failure state. Use provider idempotency only if the chosen API documents it. A provider may have processed and billed a request before a timeout prevents receipt or durable storage; the design cannot promise exactly-once billing. Record that uncertainty and apply the authorized bounded retry policy instead of treating the timeout as valid cached output. Durable checkpoints prevent avoidable repeat calls after known success, not every possible charge. [A1-A2]

Proposed conservative defaults are a 12-second fetch timeout, 2 MB decompressed HTML cap, one concurrent request per host, low overall concurrency and three transient attempts with exponential backoff plus jitter. Configure JSON/ICS-specific caps and pagination limits from actual source needs. Respect Retry-After even when it exceeds an invocation budget: persist the next attempt instead of sleeping or retrying early. Retry transient timeouts, 429 and selected 5xx; treat invalid credentials, explicit denial, malformed content and identity ambiguity as source or record exceptions. These are starting settings to measure, not benchmark claims.

Bound wall time, CPU, bytes, pages, redirects and recurrence expansion. Measure the enabled workload against the actual Cloudflare plan before hosted activation. Workers limits differ sharply by plan and trigger interval; free capacity is not assumed. If due-job batches fit, keep the job-table design. Add one Queue only when independent retries or backlog exceed that simple approach. If used, assume at-least-once, unordered delivery, persist failures outside finite queue retention, acknowledge only committed successes and use a durable outbox to avoid a D1-write/enqueue gap. Workflows and browser rendering are optional further tools, not required stages. [S12-S16]

Keep immutable normalized revisions and minimal evidence in D1 initially if size/retention measurements fit. Use private R2 objects for larger permitted snapshots; never expose them through the existing public MEDIA/avatar route. A separate private evidence bucket is preferable when isolation cannot be proven. Write the immutable object before a database reference; a crash may leave an unreferenced object but must never publish a missing one. No distributed atomicity across D1, R2 and Queues is assumed. [R9; S13; S17]

For each accepted event, stage its complete immutable revision, then atomically change its current publication pointer using an expected-version comparison. Include identity mapping and any compatibility projection in the same D1 transaction. Guard all related writes against the same expected version; a zero-row compare-and-swap must not permit side effects from a losing writer. A delayed job cannot overwrite a newer notice. Before publication, recheck current source/notice observations, interpretation context, authority, conflicts and the expected publication version. If one changed, invalidate the affected reconciliation and rerun it; extraction can still be reused only if its own key remains valid. D1 batch transactions provide database atomicity only. Publish independent healthy events without waiting for an unrelated source, while keeping a single occurrence internally coherent. [S13]

The event repository reads one publication revision per occurrence for every consumer. Migrated records bypass hard-coded legacy overrides; unmigrated records remain an explicitly labeled baseline. Keep current no-store behavior initially rather than add cache invalidation complexity. If caching is introduced later, include the publication revision in cache keys. Return no fabricated map points or schema values. Expose safe source links, last checked, uncertainty and cancellation/postponement on list, detail and calendar views.

Rollback has two controls: the compatible Worker version and the event publication pointers. Record the previous pointer with each publication, and change it back under a version guard when a bad revision is found. Freeze only the affected adapter/record writer unless a schema-wide integrity failure exists. Worker rollback alone does not undo D1 or R2 state. Additive schema and retained revisions must let the previous reader run without losing member data. [S18]

## 8 Validation security and operational evidence

Validate each candidate before publication: supported source and occurrence identity; parseable date/precision/timezone; end order; allowed status; Texas location basis; type/unit bounds; provenance for every claimed fact; authorized URL schemes and host rules. Required-field failure quarantines that occurrence. Optional-field failure becomes null plus a reason. Keep successful source observations and healthy records; do not make quarantine a global publication veto.

Use parameterized SQL and output escaping. Reject credential-bearing URLs, private-network targets and unsupported schemes; revalidate approved redirects, resolved addresses and linked downloads. Bound decompressed bytes, redirect depth, HTML/ICS/JSON nesting and geometry point counts. Registry edits and publication/rollback controls require the application's restricted operator path or protected service entry point, not a public fetch endpoint. No public “refresh any URL” function. Exclude attendee data, credentials and private account content from ingestion and logs. Source instructions cannot change extraction policy. [T21-T24]

Log run/source/job/representation/extraction/occurrence/revision IDs, stage durations, fetch outcomes, bytes, producing versions, accepted/rejected/unchanged counts, retry reasons and publication results. Include cache hit/miss and invalidation reason, checkpoint resume stage, shared-request wait/recovery and model escalation reason. Generate routine summaries from these counters in code; no normal-path model report is needed. [A5; A7] Keep a simple queryable report before buying a monitoring service. Alert on a missed due refresh, expired lease, unresolved retry exhaustion, sustained backlog or a publication failure; deduplicate repeated alerts by source and cause. Healthy-source publication should continue during an alert.

Measure requests and model calls/input/output tokens separately for extraction, reconciliation if a model is ever justified there, and reports. Break out retries, recovery, cache hits and invalidations; include failed attempts rather than counting only successful calls. Report totals and per correctly completed occurrence for equivalent completed work. Cached input and reasoning tokens may be subsets of provider input/output totals: preserve provider definitions and avoid double counting. Model discounts change price, not necessarily logical token consumption. Record dollars, latency and bandwidth separately. [A7] The cost model is enabled sources x checks x pagination/detail requests x retry factor, plus bytes retained, D1 reads/writes, any queue operations, browser time and model tokens. Record actual p50/p95 duration, worst observed CPU, row counts and total daily cost estimates during a bounded pilot. No savings percentage, free-tier promise or statewide-capacity claim is currently proven. Price the chosen services from current account entitlements and official prices; an optional paid adapter can remain disabled. [S12; S19]

### Bounded equivalence and usage comparison

Compare the existing efficient design in this plan with each proposed optimization using the same permitted captured fixtures, injected clock, source/authority configuration, discovery horizon, desired facts and required checks. The baseline already uses deterministic extraction and relevant excerpts; do not invent an always-model or whole-page baseline to inflate savings. Include normal deterministic runs, unchanged and changed evidence, a cancellation absent from stale metadata, source failure and recovery, replay after a downstream crash, concurrent shared requests, context/edition/timezone changes and a notice arriving during recovery. Add conditional-path cases only when that option is proposed for use.

Compare full facts and null/value states, status, identity, conflicts, quarantine, freshness, coverage, publication behavior and retained evidence references against captured source truth. Ignore incidental run IDs, timing and cache markers; producing versions are intentionally different. Correct an unsupported baseline fact rather than claiming equivalence with it.
